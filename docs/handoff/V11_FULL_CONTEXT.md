## 2. 当前运行架构和历史参考实现不能混写

```text
用户浏览器
   │
   ▼
index.py → core.app (同一 Python FastAPI 前后端入口)
   ├─ 金融知识问答、资料上传、引用/来源管理
   │    └─ 文档版本/权限 → BM25 + 可用中文CPU语义检索/RRF → 可选生成与引用
   ├─ Memory / Trace / 反馈 / 受限 Skill 候选与回放
   └─ V11 Workflow API (新增)
        ├─ Input Snapshot + Request ID 防重
        ├─ Validate → (Weekly Report || Wealth Benchmark) → Verify → Report
        ├─ 服务器检查点、版本/租约防旧写、局部复用
        └─ 独立人工复核 → 获审草稿 JSON/CSV 导出

持久层：本地 SQLite；线上 V11 MongoDB 工作空间
模型层：线上 DeepSeek（仅已记录真实合成问题的单次连接/引用冒烟）
参考扩展层：engine/、jinshu/、unified/ 保留可选 Milvus / Redis / pi 等
```

- **线上默认行为：**已核对为 `index:app → core.app`，V11 Mongo 持久化；网页默认检索是 BM25 与 CPU 中文语义方案（依配置、资源可用而降级），按现有逻辑进行融合/重排与引用检查。
- **不能泛化为线上全部组件已运行：**参考工程具备 Milvus、Redis Stream、pi Agent Runtime、K8s/HPA、Prometheus 相关实现或规划，不意味着当前 Vercel 每次请求都经过这些组件。尤其不可以把保留参考文件、曾经本地联调、现在生产运行三者混作同一成果。
- 模型不可用时部分确定性工具仍能运行；环境变量只表示配置，连接成功、实际推理、引用正确和真实回答质量是四个不同证据层。

## 3. 原有治理底座：可信 RAG、Memory、Skill 和 Loop

**可信 RAG：**文档进入前检查权限、版本与状态；资料来源和原文被独立管理，检索命中需要可回查、不可将归档/未审核信息当正式制度。关键词检索解决编号、日期和精确字段；语义检索提升改写与口语提问召回；引用编号存在不等于事实内容全部正确。

**Memory：**区分已审核事实、会话上下文、明确用户偏好、组织知识与程序策略。会话摘要或模型推断不可直接当作官方来源；上下文需要权限、时效、证据权威和长度预算控制。

**反馈自进化 Loop：**
`Execute → Observe → Reflect → Adapt → Deploy`，即执行→观察反馈→按 `retrieval / intent / generation / knowledge_gap` 归因→形成受限候选→历史 Trace 回放、人工审核、灰度及回滚。可调整查询扩展词、检索 top-k、表达模板，知识缺口应补资料而非编规则。所谓**自进化是下一次请求的策略变更，不是训练模型权重或自动批准金融业务制度**。部署方式和候选质量需要按真实运行版本确认。

**不要混淆两种循环：**V11 的任务 DAG 组织**一次业务任务**；反馈 Loop 根据历史失败改进**下次 Agent 执行**。两个机制互补，不需要为了追「Graph Engineering」强行增加多 Agent 或新框架。

## 4. V11 的核心实际改造：可恢复金融业务工作流

### 4.1 业务过程

主要复合场景：**周报质检＋同业业绩对标**，使用明确用户输入或项目合成示例，先检查字段/口径，再处理两个无互相依赖的计算分支，汇总规则校验和复核包：

```text
请求标识和输入快照
       ↓
Validate（字段、来源、输入指纹）
       ↓
Weekly Report ─────┐
Wealth Benchmark ──┴──→ Verify → Review Package
                                 ↓
                         等待另一个账号审阅
                                 ↓
                      只导出当前获审 JSON/CSV 草稿
```

另外原有**八类确定性业务工具**可单独走同一流程；合成数据必须显式选择，不是金融机构生产数据，也不会调用真实支付、交易或产品发行指令。

### 4.2 请求防重、检查点与恢复

- `request_id` 按工作区所有者、登录账号及输入指纹去重。同键同输入复用任务；同键不同输入返回冲突。删除任务后不承诺永远记住该键。
- 节点结果、依赖、状态、尝试次数、耗时、输入哈希、实施代码哈希及审核记录落服务器持久状态。一个 HTTP 请求推进一个有界批次，无后台永久自动唤醒。
- **45 秒租约、每节点最多 3 次尝试、约 20 秒节点预算**。执行中断时，后续请求在租约过期后恢复；已成功持久保存且依赖不变的纯计算节点可以复用，未保存成功的计算可能重算。
- 同一任务输入或代码改变后生成新版本，旧审核必须失效；只复用指纹一致的节点，后续校验/复核包重新生成。旧计算完成太晚时按版本和执行租约拒绝其写回。
- 曾有专门测试杀死子进程，随后由新实例读取并恢复；另测试了「最后结果写入了检查点、批次完成标记尚未写入」的中断场景。
- **执行边界：**不是整个 LLM 执行的 durable 引擎；没有外部写操作 exactly-once 保证。支付、发邮件、真实风控处置绝不能用「不确定就当成功」模式。

### 4.3 金融规则和人工复核

- 发行业务排期校验：显式日历版本、覆盖起止日期、工作日例外、募集/成立/到期顺序、日期调整以及多批次冲突。日历不全如实提示，不让模型猜测节假日。
- 业务金额与收益由白名单**确定性工具**计算，不让语言模型生成随机数字；输入中缺少的收益率保留缺失，不默填零。
- 三档质量标签：`KEEP`＝规则未发现问题，仍需人工审阅；`REVIEW`＝有待检查项；`REWRITE`＝硬校验失败，禁止审核批准和导出。**这不是 80%/90% 模型置信度阈值。**
- 提交者不可自审。审核绑定结果、输入和代码版本；导出只读取服务器保存的已批准结果，绝不采用浏览器传回的伪造产物。
- 用户可看到节点状态、错误原因、尝试次数、复用标记、审核记录。运营指标仅是任务提交/待审/审批/阻断/尝试/复用等过程统计，**不是模型准确率、实际用户解决率或效率收益**。
- 本版原型对单个输入/任务数量和全局存储设置了上限。进一步扩容需要拆分任务集合并加容量/并发测试，不是当前已做的大规模生产系统。

## 7. 简历表述、面试准备与归因的统一要求

**简历优先体现四组事实：**
1. 业务方案：知识查询、发行支持、核查辅助；PRD/交互、输入/异常/人工复核边界。
2. RAG/知识与反馈运营：资料权威、版本、引用；受限策略候选、Trace 回放和发布回滚。
3. 可靠的可执行业务任务：八类白名单工具、周报＋同业对标复合 DAG、请求防重、检查点、局部重算、独立复核与导出。
4. 验收与运营观测：结构化错误、执行记录、规则质量分流和特定回归用例。测试层次严格区分；不虚构收入、成本节省或用户成功率。

**面试有必要讲清楚：**原工程 vs 本人贡献；为何这条流程用确定性 DAG 而不是自由 ReAct；Graph 与运营 Loop 的职责区别；CAS 与租约/旧结果隔离；崩溃后哪些步骤可重试；为何写操作不能承诺 exactly-once；如何判断 `KEEP/REVIEW/REWRITE`；为何发行业务不盲用 CP-SAT；文档权限和来源为什么不能由 Memory 取代；以及真实模型证据仅是小规模冒烟。

可以使用 `docs/RESUME_PROJECT.md` 提供的四条及三条简历版本；`docs/INTERVIEW_MANUAL.md` 包含 60 秒中英介绍、20 道与当前代码对应的追问、演示路径。**个人完整简历 PDF/DOCX 含姓名、联系方式和照片，只保留个人私有文件，未发布在 public 仓库。**

## 8. 下一轮真实工作优先级

- **优先 A：实际业务可用性。** 将 JSON 数据输入逐渐改为对运营友好的 CSV/Excel 导入与预览、字段映射、缺失值提示、验证前后对照，但不能把真实企业数据上传公开演示。
- **优先 B：独立评测。** 固定带版本的金融业务数据集，区分「函数通过」「证据有效」「模型答案质量」「审核完成」；进行人审抽样，不拿点踩率替代真实准确率。
- **优先 C：服务可靠性。** 改造当前单事实文档式任务存储，拆成 run/node 集合，补并发容量与失败恢复测试；真实部署时再评估是否需要 Redis Worker 或 durable 框架。
- **优先 D：运营与交付。** 让问题归因/复核队列可操作、能查看变化前后对照，增加可读交付物、日志可观测与模型成本透明度。
- **优先 E：简历与面试。** 根据招聘目标（Agent工程 / AI产品 / 金融中后台）调整技术密度，但始终保证每句话可以在源码或测试中找到依据。
