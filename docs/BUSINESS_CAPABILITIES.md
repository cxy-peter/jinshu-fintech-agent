# 金枢业务能力与复现索引

本页以当前仓库的 `jinshu/tools.py`、`unified/tools.py`、`core/workflows.py` 为依据。保留 V11 的任务版本、输入快照、节点检查点、独立复核与已复核草稿导出。这里的能力数目和测试结果不代表生产效果或检索命中率。

## 从业务问题进入实际功能

`core.business_catalog.catalog()` 返回八个已登记工具的业务场景、必要参数、文件名、示例问法、实现来源与边界。`suggest(query)` 只匹配明确业务词，最多建议两个工具；只预填问题中明确出现的绝对日期、期限、周期、期数等参数。未给定的信息留空，资料文件仍须用户提供或主动选择合成示例。这个接口不执行工具、不发送邮件、不调用模型猜参数。

问“FOF 是什么”属于知识检索，不能为了展示执行能力强行转成发行或投资对标任务。问“从 2026-11-09 起，期限 90 天，每两周发行，共 3 期，生成排期”则可以进入 `issuance`，并保守预填四个参数。问题同时写“每周或双周”时周期保持为空。

## 发行日与发送日采用不同规则

原有发行计算保留输入日历中的 `workdays` 调休覆盖：成立日、募集结束日、到期日按营业日调整。这有利于兼容既有业务脚本和已经确定的发行安排。

新增发送计算使用更严格的规则：**周六、周日始终禁止发送，即使该日期在 `workdays` 中；`holidays` 中的每个日期也禁止发送。** 候选日取“募集结束日及之前最近的允许发送日”。这个锚点是当前草稿的明确计算口径，需要业务人员确认，并不表示已确定发送时刻。

发送计划需要成对填写 `coverage_start` 与 `coverage_end`。未提供范围时，原有发行草稿仍可计算，但候选发送日为 `null`，状态为 `calendar_incomplete`。任何调整触及明确范围外均停止计算、要求补日历；不会把未知日期当普通工作日。日历版本、适用市场、节假日的完整性与真实性仍由资料提供方和复核人员确认。系统未接入官方日历接口，不能把合成日期当成中国法定节假日。

结果在 `send_plan` 中保留规则、日历范围、候选日期、`requires_review=true`、`sent=false`、`business_action_executed=false`。行内展示“候选发送日”与“发送计划状态”。不存在定时任务、SMTP 发件、真实邮件送达或自动批准的暗示。

### 可主动载入的 2026 年全国放假调休日历

[`core/calendars/cn_2026.json`](../core/calendars/cn_2026.json) 根据[国务院办公厅关于 2026 年部分节假日安排的通知](https://www.gov.cn/zhengce/zhengceku/202511/content_7047091.htm)逐日列出 33 个放假日期（含放假区间内的周末）和 6 个调休上班日期；保留官方来源地址、版本、说明与适用范围。来源只有该国务院通知，不以网络日历工具的推断补充日期。

这是 **2026 年全国放假调休安排**，不是交易所休市、机构营业、产品合同或跨境市场专属日历。需由用户在界面主动载入并确认适用性，不默认替换已有机构日历；官方数据与合成演示各自明确标记。所有调休周末仍被发送规则排除。

覆盖范围严格为 `2026-01-01` 至 `2026-12-31`。例如，2026 年 11 月开始的 90 天产品到期日会落到 2027 年，系统必须要求补充下一年经确认的日历，不会外推。新年起始几天若需回溯到 2025 年发送，也同样停止并要求补齐范围。此数据文件不会自行同步新的政策通知。

`tests/core/test_business_official_calendar.py` 核对全部公布日期，并遍历 2026 年 365 个起始日期：采用一期、期限一天的验证输入，359 个能够在范围内完成计算的情形均不会生成周末、调休周末或已列假日发送日；6 个需要跨越年度边界的情形明确拒绝。另验证真实常见的 90 天期限跨年输入会被阻断。这个遍历验证的是日期约束，不是发件成功率。

## 用同一任务复现完整流程与条件变化

可直接使用 [`data/synthetic/issuance_review_demo.json`](../data/synthetic/issuance_review_demo.json)。这是一个有明确标记的合成案例，文件中的调休日、休息日设定只是软件测试条件。顶层说明和预期结果不属于 API 参数；将其中的 `values` 与 `sources` 分别粘贴到已有业务任务页的对应输入区，选择 `material_fill`。

1. 录入产品名称、首次拟成立日、期限、周频率、三批次数量，以及明确覆盖到到期日的日历。
2. 创建任务并执行。V11 保存输入快照和数据哈希，先验证输入，再执行排期与材料预览，共用同一份日期计算。
3. 首批成立日为 `2026-11-09`。合成日历把 `2026-11-08` 设为营业日，因此募集结束日可在该日；候选发送日仍回退到周五 `2026-11-06`。
4. 在原任务“编辑输入”中把 `2026-11-06` 增加为合成休息日，把日历版本改为 `SYNTHETIC-SEND-DEMO-v2`。不要新建一个互不关联的问答来替代修订。
5. 重新执行后，第一批候选发送日变为 `2026-11-05`。V11 以新版本快照重新计算受影响节点，并清除旧审批；有范围不足、日期碰撞或字段缺失时明确停止或要求复核。
6. 由另一名具有复核角色的用户审核当前版本，才能导出服务端持有的已复核草稿。修改条件后须重新复核；导出仍不等于发送或发行。

现有 `wealth_review` 复合流程也已串联输入校验、周报质检、同业对标、结果核验和复核包。两个计算分支共享该任务的快照；修改周报时可复用未受影响的对标结果。这些已有 V11 结构直接满足“输入信息 → 查询资料与规则 → 校验约束 → 输出成果 → 修改条件 → 重算 → 人工复核”的关联流程，不另建一套不兼容的编排系统。

## 与历史代码的对应关系

## 验证范围

新增 `tests/core/test_business_catalog.py` 检查工具目录与登记表一致、业务明确词、最多两个建议、无执行、无静默示例、模糊或无效日期与期限不猜测；`tests/core/test_business_calendar.py` 检查调休周末禁止发送、原成立规则兼容、周与双周、已列休息日排除、覆盖范围不足、材料共用计算与修改日历后的重算。既有 `tests/core/test_workflows.py` 继续验证版本、检查点、数据快照、代码变更缓存失效、独立复核与草稿导出。没有以这些单元测试结果宣称生产业务可用率或 RAG 命中率。
