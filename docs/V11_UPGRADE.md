# 金枢 V11：保留文枢底座，补齐可交付的业务流程

## 定位与来源

金枢是基于既有文枢 Agent 工程的个人、AI辅助改造，不是从零原创整个框架，不是差旅助手改名，也没有模型训练。保留原 Harness、可信RAG、Memory、反馈—候选—回放—审核—灰度/回滚方向；`engine/`、`jinshu/`、`unified/` 的企业参考实现及来源声明未删除。

V11 的实际网页入口仍是 `index.py → core.app`，和本地一致。默认网页使用 CPU 中文向量、BM25/RRF、可选模型重排和 DeepSeek；MongoDB、私有Blob或本机SQLite承担持久状态。Milvus、Redis和原pi服务保持可选，不宣称本次已验证所有企业服务或K8s/HPA。

差旅V2参考材料中值得迁移的是：结构化输入门控、显式步骤依赖、持久检查点、请求防重、结果规则检查和失败归因。未移植其旅游领域、PostgreSQL/AgentScope或pi-durable依赖，也不继承其评测数字。附件说明写明实际仅100条单轮+3组多轮，不能用正文里的500条、Recall/MRR和线上回流数字作为金枢的证据。RAR原代码未能在本轮工作容器中取得可读副本，因此此次是基于已提供完整文字材料与金枢实际源码的独立实现，不声称完成参考RAR逐行审计。

`Intern-Python4WealthProduct` 核对到的业务依据：
- `数据月报.ipynb`：输入文件/必要列/依赖检查和数据报告流程。
- `业绩比较-五只产品对比+市场业绩对标.ipynb`：可比产品池、字段清洗、分组与中位数比较。
- `文本转二维码+产品发行排期日期要素+按照模板批量生成文件并修改word内容.ipynb`：日期排期和冲突标注。
- `产品发行书excel参数转word固定位置材料文字替换.ipynb`：材料字段填充与日期口径。

这里只参考业务模式，没有复制内部产品数据、路径、Notebook输出、邮件发送或公司模板到公开应用。当前排期规则是显式输入日历下的项目规则，不等于实习机构的全部发行规则。

## 新增的可用交付

`core/workflows.py`、`core/workflow_api.py`、`core/web/workflows.js` 接入同一应用。网页新增“可恢复业务流程”：

```text
请求标识 + 输入快照
         ↓
输入检查/字段门控
         ↓
周报质检 ─┐
同业对标 ─┴→ 规则校验 → 复核包汇总 → 等待另一账号复核 → 版本化 JSON/CSV
```

八类已有工具可以单独走同一任务框架；复合周报任务不把两张不同业务表强行合并，只并行执行独立检查，最终组成一个复核包。金额和收益计算依旧来自确定性函数，模型不在新任务执行路径里猜数。

### 请求防重与恢复的准确边界

请求键按浏览器所有权、登录账号和显式request_id隔离。同键同输入返回既有任务；同键不同输入返回冲突。不能以“问题文字相同”永远阻止合法的新任务。任务删除后不再承诺该键继续防重。

输入、节点结果、依赖、尝试次数、耗时、事件及审核凭据保存在原事实存储中。SQLite以事务写入；Mongo/私有Blob走既有CAS。每次HTTP最多执行一个有界批次，独立步骤并行；完成一个节点就保存一个检查点。执行租约45秒，旧执行结果通过租约ID及输入版本校验隔离。单节点最多3次尝试、20秒计算预算。

服务中断后需新请求触发恢复。不是Vercel里启动永久线程，也不是关浏览器后必然自动继续。只有纯计算/只读工具允许重跑；外部支付、发邮件、模型生成不在此恢复机制内。检查点提供可恢复进度，不等于跨系统exactly-once。结果可能算过但没保存时重算，不能谎称从不重复计算。已保存最终节点但未更新任务状态的中断，也从检查点收敛到待审或阻断，不重复计算。

输入改动：清除旧复核，生成新版本；只复用输入指纹与实现哈希都未变的已完成节点。代码版本变化后也要重核。导出读取服务器保存的获审结果，不相信浏览器提交的结果JSON。下载在读取时核对版本；已下载的文件不能远程撤销。

### 质量分流不是置信度

KEEP：当前规则未发现问题，仍需独立人员复核。REVIEW：缺失值、日历适用性、模糊匹配或候选规则需核验。REWRITE：算术恒等式或必需字段硬校验失败，阻止批准导出。没有“80%置信度”或模型自报分数。

排期新增：工作日例外、日历起止范围、互斥日期检查、募集/成立/到期顺序、顺延导致重复批次、有限搜索预算。未提供完整日历范围时明确提示。固定周期排期先用规则，不为简历而增加CP-SAT；需要多个产品竞争同一天容量等组合约束时再建优化模型。

### 运营可看到什么

任务列表、节点失败原因、当前步骤、尝试次数、耗时、复用标记、租约恢复事件、输入哈希、代码哈希、审核人和复核意见。本人任务指标仅统计提交、待审、获审、阻断及重试/复用，不把这些统计称为正确率或提效成绩。

现有问答Loop继续用于跨任务的策略改进；工作流则组织一次业务任务。二者互补，不替换模型权重，也不自动修改金融事实、权限和审核规则。

## 验收

- `python -m pytest -q tests/core`：原有功能加新任务API/版本/权限/防重/进程中断/日历测试。
- `python tests/core/browser_check.py`：既有网页回归。
- `python tests/core/browser_workflows.py`：实际HTTP上的任务保存、刷新恢复、独立复核、下载和移动端。
- `python scripts/build_unified.py`：生产依赖冷启动检查，无模型调用。
- 部署验收另记版本、Git SHA、实际URL、数据库类型和真实接口返回；构建READY不等于模型质量通过。

本轮未进行压测、真实业务试点、随机对照效果估计或实时金融系统集成。任务存储是有上限的原型事实文档（全局8MB）；每浏览器最多20个任务、总计100个，输入180KB。进一步扩容应拆独立run/node集合，不能把单状态文档当大规模工作流数据库。

## 为什么没有照搬参考文档的部分说法

1. “不可重放就跳过写入”最多降低重复副作用风险，不能同时证明不重复且不丢失。外部写入应使用下游幂等键/收据/待核实状态，而不是把未知当成功。
2. CP-SAT只保证已建模且输入正确的约束；UNKNOWN不同于已证明INFEASIBLE，求解超时不能直接说无解。
3. 本地SQLite执行状态不能当Vercel持久化；本项目线上使用已有Mongo事实存储。
4. 规则命中、引用编号合法、Judge评分、真实用户解决和业务正确性是不同指标。
5. 未实现或未验收的K8s、HPA、自动主动服务、线上日志全量回流不能写入成果。
