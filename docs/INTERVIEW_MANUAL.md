# 金枢 V11｜面试准备与演示

## 60秒介绍

金枢是我基于既有文枢工程改造的金融中后台知识与业务辅助Agent。我关注的不是让模型自由处理金融业务，而是把知识依据、固定计算和人工复核接成可核查的流程。原有系统保留资料审核、混合检索、引用和反馈策略回放。这一轮我参考差旅助手的可靠执行思想，增加了周报质检与同业对标的复合任务，把输入版本、节点结果和复核凭据保存在服务器。重复请求不会重新建任务；执行中断后可以请求恢复，输入改变只重算受影响部分，旧审批失效。我主要负责业务场景、流程和规则设计、测试验收，使用AI辅助代码实现。没有模型训练或真实金融机构生产试点。

English: Jinshu is a personal financial-operations assistant adapted from an existing agent project, with AI-assisted implementation. I focused on business workflows, source governance, and testable controls. It combines reviewed knowledge retrieval with deterministic tools for tasks such as report checks and product benchmarking. The latest version adds server-side checkpoints, request deduplication, and version-bound independent review. It can resume supported business tasks after an interruption without treating an uncertain result as success. This is a working prototype, not a model-training project or a bank production system.

## 20个高频追问

### 1. 哪些是原工程，哪些是你这一轮新增？
原工程提供Harness、RAG、Memory、Loop及服务框架；金枢做金融业务适配。这一轮新增的是当前工作台里的检查点任务服务、复合周报流程、请求防重、输入与代码绑定、独立任务复核、排期规则检查和专项测试。不能把整个框架说成从零原创。

### 2. 为什么不直接把差旅V2整套搬来？
业务和部署形态不同。差旅的时间窗/预算问题可用约束求解；金枢当前固定发行频率更多是日历与输入规则。借用问题的解法，不盲目叠AgentScope、PostgreSQL、CP-SAT、pi-durable四套依赖。原知识治理与Loop没有替换。

### 3. 一个复合任务具体怎么跑？
保存产品、观察区间、周报表、产品表和净值表；先检查结构，再并行处理互不依赖的周报质检和同业对标，规则校验后汇总复核包，等待另一账号审核，最后导出。各步骤分别留状态、输出和耗时。缺数据不是让模型补数字。

### 4. 你用Graph框架了吗？
没有新引入LangGraph。当前是确定性依赖图和显式状态机，节点均为已有Python工具。选择普通代码是因为任务收敛、当前需求有限。以后需要通用长流程、事件驱动、多层子图时再比较框架，不以框架名作为先进程度。

### 5. 检查点保存什么？
任务输入快照、输入哈希、代码哈希、流程版本、节点依赖、结果、状态、尝试次数、耗时、事件和审批。等待或中断后，新请求读取这些记录继续，不依赖上一条HTTP请求还活着。

### 6. 为什么不是Redis锁就够了？
锁只能协调执行，不能替代结果持久化和版本判定。这里原事实存储做CAS，租约标识用于排斥旧执行，已完成结果保存为检查点。锁过期后仍要检查旧工作者是否有权写回。

### 7. 能保证exactly-once吗？
不能泛化。相同用户/请求标识防止重复创建，CAS防止重复确认或旧结果覆盖。纯计算在“计算完但检查点未保存”时可能重跑。没有接支付、发邮件等外部副作用；这类操作还需要下游幂等键和收据，未知结果应待核实，不能直接当成功。

### 8. 如何测试崩溃恢复？
测试让子进程完成输入检查后，在工具执行中直接退出。新实例读同一SQLite，待测试时钟越过租约后恢复；已保存节点不重跑，未完成节点重试。另有并发旧结果被输入新版本拒绝，以及最终检查点已写但状态未更新的恢复测试。SQLite测试不能自动代表Mongo分布式压测。

### 9. 用户改了一项输入，会全部重算吗？
节点指纹只包含它真正消费的参数、数据和实现版本。只改周报名称时，对标结果可复用，周报和后续校验/汇总重算。修改输入必然清除审批。不是只根据“这轮用户说replan”就复用全部P1结果。

### 10. 为什么需要独立复核？
规则只能检查已经编码的条件，不能确认数据本身真实性或业务适用性。提交者不能自审；审批绑定输入版本、输出哈希和代码实现，修改后必须重新核对。批准的是草稿，不代表下达发行或风控指令。

### 11. KEEP、REVIEW、REWRITE如何判断？
KEEP指当前规则没有发现问题，但仍须复核。REVIEW指缺失值、日历适用性、模糊匹配等待确认问题。REWRITE指硬校验失败，禁止批准和导出。它们不是0.8之类的模型置信度阈值。

### 12. 排期为什么没上CP-SAT？
当前规则是固定周/双周频率、工作日顺延、日期顺序及冲突检查，先用确定性计算最清楚。若多个产品竞争发行容量、必须满足销售窗口和到期分布等组合约束，才值得建求解模型。求解器也只保证被建模的条件，UNKNOWN不是证明无解。

### 13. 如何保证RAG可信？
资料要有来源、版本、有效期和审核状态，检索候选再回到有效原文。向量负责语义，关键词补精确信息，融合重排后回答附引用。但引用编号存在不等于回答全部事实正确，重要结论仍要核查。

### 14. “自进化”到底进化了什么？
不是模型权重。历史未解决反馈由运营归因，形成受限查询扩展、top-k或回答结构候选，经同批回放和独立审核灰度。知识缺口先补资料，不让策略编造制度。现有网页是受控的人在环迭代，不应称全自动自训练。

### 15. 为什么有Memory仍要版本校验？
会话摘要、偏好和历史回答不是正式制度。即使用户说“沿用上次”，仍要检查资料和输入是否变化。缓存或前序结果能复用，需要验证其所依赖的信息没有改变。

### 16. 线上和本地是不是两份逻辑？
当前都运行index:app，业务节点相同；本地可用SQLite，线上使用已配置的持久化服务。Vercel临时盘不用于持久任务。企业参考Runtime仍保留但不等于全部组件都在默认线上请求里运行。

### 17. 为何每次只推进一个批次？
避免把整条长流程绑定到一个请求，也便于在用户复核前结束请求。每步检查点可读，页面可以恢复。当前不会在后台永久运行，也没有自动事件唤醒Worker，这一点明确作为边界。

### 18. 运营如何使用，不懂代码行不行？
看步骤表、失败原因和质量标签，补缺失数据、调整输入、提交复核、下载结果；反馈页可提出受限策略候选。目前自定义数据使用JSON输入，非技术操作人员仍需模板与引导，不能称零学习成本。运营不能关闭权限和硬校验。指标记录提交、待审、获审、失败、尝试和复用，不把获审率叫业务正确率。

### 19. 有哪些效果数字？
只能引用与当前提交绑定的CI、浏览器和部署证据。程序回归不等于回答准确率，真实模型接口返回不等于系统质量验收。没有借用参考项目的500条、91%、Recall/MRR或线上用户数据；旧金枢489/500只作为历史开发记录。

### 20. 最值得继续优化的是什么？
优先把单文档事实存储拆成独立任务/节点集合，完善真实业务标注集、接口级幂等和审核权限范围；有需要再做外部Worker与事件驱动。比新增框架更重要的是在故障、版本变化、无依据时不产生错误成功状态。

## 页面演示顺序

登录编辑账号 → 可恢复业务流程 → 填入合成示例 → 保存 → 执行输入批次 → 刷新页面恢复 → 执行周报/对标批次 → 校验 → 汇总 → 切换审核账号 → 复核队列 → 确认并导出 → 修改输入观察旧确认失效。

再演示硬错误：年度财务表的资产负债不平衡，显示REWRITE并阻止批准；日历覆盖不够时停止排期，不猜未来假期。
